\begin{abstract}
Applications that hold local copies of several server resources must periodically bring all of them up to date. HTTP offers no standard way to say, for many resources at once, ``this is what I already have; send only what changed.'' Related efforts address parts of this space: Braid-HTTP lets a \texttt{GET} carry a baseline version for one resource, Mercure and Events Query push updates over long-lived connections, and JMAP defines a complete application protocol. We describe SYNC, a query format for the HTTP \texttt{QUERY} method (RFC~10008): the client declares a baseline for each of many resources in one request, and the server returns an independent result per resource (a JSON Patch, a JSON Merge Patch, or a full representation), with no long-lived connection and no failure coupling between resources. Building on \texttt{QUERY} rather than a new method gives SYNC defined caching and conditional-request semantics and lets it run on existing servers and browsers. We present the format, a reference implementation for Node.js and browsers, a security analysis, and a measurement against the \texttt{braid-http} library and the Mercure hub over real sockets with simulated latency. To catch up 100 resources after one round of change with minimal headers, SYNC used 1.0\% of the bytes of full polling, comparable to the Mercure hub (1.1\%) and below per-resource Braid requests (2.8\%); when many changes accumulated, Braid's item-level patches were smaller. With realistic request headers and compression, SYNC used 1.0\% against 4.7\% for Mercure and 20.4\% for Braid, although part of that gap reflects the other systems not compressing by default. For a single resource SYNC offers no consistent advantage.
\end{abstract}

\section{Introduction}

Applications that keep local state synchronized against a server (feed readers, mobile apps resuming after being offline, dashboards, configuration agents, caches) share a common step: the client holds copies of several resources and needs to bring them current. Most of the data it would receive is data it already has.

HTTP offers two standard tools for this. A plain \texttt{GET} returns the full representation every time. A conditional \texttt{GET} with an entity tag returns either the full representation or \texttt{304 Not Modified}~\cite{rfc9110}, so a resource that changed in one field is re-sent in full. Applications therefore either accept that cost or build application-specific mechanisms.

This is not an unexplored problem, and we do not claim it is. Section~\ref{sec:related} surveys related work: Braid-HTTP~\cite{braid} already lets a client send a \texttt{Parents} header on a \texttt{GET} and receive only the updates since that version, for one resource at a time; Mercure~\cite{mercure} and Events Query~\cite{eventsquery} deliver updates over long-lived connections; JMAP~\cite{rfc8620} and WebDAV collection synchronization~\cite{rfc6578} provide ``changes since a state token'' within their own protocols.

SYNC targets a narrower point in this space: a \emph{stateless pull} that names \emph{many resources in one request} and returns an \emph{independent result for each}. It is meant to compose with subscription mechanisms rather than replace them: a client resuming after a disconnect can catch up on all of its resources in one request and then subscribe for live updates.

An earlier version of this proposal, posted to the IETF HTTP working group, defined a new HTTP method. Discussion there asked how it differed from the \texttt{QUERY} method~\cite{rfc10008}. It did not differ in any way that matters, so SYNC is now defined as a query format for \texttt{QUERY}. Section~\ref{sec:design} explains the consequences.

\paragraph{Contributions.}
\begin{itemize}
  \item A query format for \texttt{QUERY} that carries a baseline per resource and returns per-resource results in a negotiated update format, with defined scope, authorization, error, caching, and fallback behavior (Section~\ref{sec:design}).
  \item A reference implementation: server middleware for Node.js, and a client built on \texttt{fetch} that runs in browsers and Node.js (Section~\ref{sec:impl}).
  \item A measurement against the \texttt{braid-http} library, the Mercure hub, and baselines, on real sockets, under minimal and realistic header and compression conditions, including conditions where SYNC does \emph{not} help (Section~\ref{sec:eval}).
  \item A security analysis of client-declared-baseline catch-up that states which mitigations the reference implementation enforces (Section~\ref{sec:security}).
\end{itemize}

\section{Related Work}
\label{sec:related}

\paragraph{Conditional GET and delta encoding.}
Entity tags~\cite{rfc9110} give a binary answer. RFC~3229~\cite{rfc3229} adds delta encoding to \texttt{GET}, but the server selects the baseline from its own history and the client cannot declare which version it holds; deployment was minimal.

\paragraph{Braid-HTTP.}
Braid~\cite{braid,braidversions} generalizes HTTP towards state synchronization with versioning (\texttt{Version} and \texttt{Parents} headers forming a version history that is a directed acyclic graph), updates as patches or snapshots, subscriptions, and merge types for CRDT and operational-transform behavior. A \texttt{GET} with a \texttt{Parents} header returns the updates since that version. This is the closest prior art to SYNC for a single resource, and Braid covers much more: live updates and multi-writer merging are outside SYNC's scope. Braid requests are per resource; its multiplexing extension~\cite{braidmux} carries many subscriptions over one connection, while each resource is still requested individually.

\paragraph{Mercure and Events Query.}
Mercure~\cite{mercure} is a publish/subscribe hub over Server-Sent Events with topic matchers, OAuth-based authorization, and resumption from a hub-wide event identifier; it replays the events published since that identifier and requires a held connection. Events Query~\cite{eventsquery} uses \texttt{QUERY} to return a representation and a notification stream from a single resource. It lists multi-resource delivery as a limitation and places versioning and resumption out of scope. SYNC uses the same method for the pull-based, multi-resource case.

\paragraph{JMAP and WebDAV synchronization.}
JMAP~\cite{rfc8620} defines \texttt{/changes} methods returning changes since a client-supplied state string and batches method calls in one request, within its own object model and endpoint. WebDAV collection synchronization~\cite{rfc6578} provides a synchronization token for the members of one collection. SYNC is a generic format for arbitrary resources identified by URI.

\paragraph{WebSockets, SSE, and application-level schemes.}
WebSockets~\cite{rfc6455} and Server-Sent Events provide push over persistent connections. Application-level schemes such as CouchDB's replication protocol and the delta queries of Microsoft Graph demonstrate demand but are not interoperable across APIs.

\section{Design}
\label{sec:design}

\subsection{Why QUERY, Not a New Method}

RFC~9110 asks that new methods be generic and that their definitions state their caching, conditional-request, and range behavior~\cite{rfc9110}. A request that is safe and idempotent and whose content describes what to return is exactly what \texttt{QUERY} provides, together with defined caching (with the request content in the cache key), conditional requests, and a way to give results a URI~\cite{rfc10008}. A new method would add none of these and would be rejected by parsers and intermediaries that do not know it: Node.js~26 rejects an unknown method in its HTTP parser before application code runs, even with its lenient parser option, while it accepts \texttt{QUERY}. SYNC is therefore a media type, \texttt{application/sync-baseline+json}, sent with \texttt{QUERY} to a \emph{sync resource}.

\subsection{Request}

\begin{lstlisting}[style=code]
QUERY /sync HTTP/1.1
Content-Type: application/sync-baseline+json
Accept: application/sync-result+json

{
  "baselines": { "/users": "a4f2", "/posts": "7b1e", "/config": null },
  "accept": ["application/merge-patch+json",
             "application/json-patch+json"]
}
\end{lstlisting}

A \emph{baseline} is an opaque version token naming the state the client holds, or \texttt{null} for none. (The earlier proposal called this structure a ``version vector''. That term denotes per-replica counters in distributed systems, which this structure is not, so it was renamed.) Tokens are opaque to clients, so counters, content hashes, entity tags, or Braid version identifiers can all be used.

Resource names are absolute-path references on the origin of the sync resource; absolute URIs and network-path references are rejected, so a request cannot name another origin. The sync resource defines which names are in scope. Each named resource is subject to the same access control as a \texttt{GET} of it by the same requester, and a resource the requester may not read is reported exactly like one that does not exist. Following RFC~10008, content that is not valid JSON is rejected with \texttt{400}, valid JSON that does not describe a valid request with \texttt{422}, and a sync resource advertises the format with \texttt{Accept-Query}.

\subsection{Per-Resource Results}

\begin{lstlisting}[style=code]
{
  "results": {
    "/users":  { "status": 200,
                 "format": "application/merge-patch+json",
                 "from": "a4f2", "to": "c93b",
                 "data": { "1": { "email": "new@example.com" } } },
    "/posts":  { "status": 304, "to": "7b1e" },
    "/config": { "status": 200, "format": "application/json",
                 "from": null, "to": "5d0e", "data": { "timeout": 30 } },
    "/gone":   { "status": 404 }
  }
}
\end{lstlisting}

The response is \texttt{204} when every resource is unchanged and \texttt{200} otherwise. Per-resource statuses are \texttt{200} (update present), \texttt{304} (unchanged), \texttt{404} (absent, out of scope, or not readable), and \texttt{409} (baseline unrecognized, only when the client disables recovery). By default an unrecognized baseline is answered with a full representation, so the client recovers in the same round trip. A failure for one resource never affects the others. This is what makes batching useful in practice: with a single status for the whole request, one stale token among a hundred would force the client to retry everything.

\subsection{Update Formats}

Three formats are defined: JSON Patch~\cite{rfc6902} (whose paths are JSON Pointers~\cite{rfc6901}), JSON Merge Patch~\cite{rfc7396}, and a full representation. The client lists acceptable formats in preference order. For each resource the server uses the first format in which the change is expressible and sends the full representation when the update is not smaller. Merge Patch cannot express a \texttt{null} member, so such changes are sent in the next preferred format.

The model (a baseline per resource, a result per resource) does not depend on media types, but the result format carries updates as JSON values, so it serves JSON representations. Other representations, such as Markdown or HTML, need a result format that can carry arbitrary content types and patch types, for example a multipart framing carrying Braid range patches. We leave that as an open question rather than claim generality we have not specified.

\subsection{Interaction with HTTP}

\textbf{Caching.} \texttt{QUERY} responses are cacheable, and the cache key includes the request content~\cite{rfc10008}. Clients holding the same baselines and authorized for the same data receive identical results, so a shared cache can serve many clients that synchronize from the same state. Because results usually depend on the requester's authorization, such responses must not be stored by shared caches unless the data is the same for every requester; the reference server sends \texttt{no-store} unless configured otherwise.

\textbf{Result URIs, conditional and range requests.} A server may give the results, or the query, a URI with \texttt{Content-Location} or \texttt{Location}, after which \texttt{GET} retrieves them; such URIs must not embed tokens or resource names. Conditional requests apply to the results as for any \texttt{QUERY}; per-resource conditions are what baselines express, and a server may use a resource's strong entity tag as its token. Byte ranges are of little use for results; a \texttt{Sync-Delta-Complete} Structured Field Boolean~\cite{rfc9651} signals that some results were deferred.

\textbf{Fallback.} Where a server or intermediary does not yet support \texttt{QUERY}, the same content can be sent with \texttt{POST}. A client tries \texttt{QUERY}, falls back on \texttt{400}, \texttt{404}, \texttt{405}, \texttt{415}, \texttt{501}, or a dropped connection, and remembers the choice per origin. The fallback forgoes caching and automatic retry by intermediaries.

\textbf{Client behavior.} Before applying a patch, the client checks that the result's \texttt{from} equals the baseline it holds; a response replayed from a cache or computed against another baseline would otherwise silently corrupt its copy. If applying any operation fails, its copy is left unchanged.

\section{Reference Implementation}
\label{sec:impl}

The server side is a request handler for Node.js, usable as Express middleware or around a plain handler, that serves SYNC requests sent with \texttt{QUERY} or \texttt{POST} and passes every other request on. Its data source is a store with two functions, ``current state'' and ``state at token'', either of which may be asynchronous. Each call receives the request context, so the store can authorize per resource, and a store that cannot rebuild an old state simply causes a full representation to be sent. The handler enforces limits (100 resources, 64\,KiB of content), sends \texttt{Accept-Query}, compresses large results when the client accepts gzip, and can answer RFC~10008's \texttt{400} and \texttt{415} errors itself when mounted on a dedicated sync resource.

The client is built on \texttt{fetch}. Given a list of resource names it returns their current values, tracking tokens, applying patches, discarding results that do not match its baseline, and asking again from scratch when needed. It can serialize its state, so a reloaded application resumes with patches instead of full downloads. We verified it in Node.js and in Chromium, where the page issued genuine \texttt{QUERY} requests. Both parts are published as an npm package with TypeScript definitions.

For comparison, the implementation also retains an experimental dedicated \texttt{SYNC} method. Because Node.js rejects unknown methods in its parser, this requires accepting raw TCP connections and handing non-\texttt{SYNC} requests to the HTTP server, an illustration of why a new method is costly to deploy.

A suite of 93 automated tests covers per-resource failure isolation, format negotiation and fallback, the \texttt{QUERY} and \texttt{POST} transports and the fallback between them, RFC~10008 error behavior and \texttt{Accept-Query}, resource-name validation, per-resource authorization through the store context, limits, compression, keep-alive, clients that half-close their connection, the high-level client (persistence and resumption, deletion, evicted history), and end-to-end application of results against server state. Writing the suite exposed three defects in earlier versions of the server, all fixed and covered by regression tests: a request body of \texttt{null} crashed the process, request bodies passed through to the application could be silently dropped while an internal connection was being established, and a client that half-closed its connection never received a response.

\section{Evaluation}
\label{sec:eval}

\subsection{Setup}

A client holds $N$ resources at round~0, each a JSON object of 100 items (about 20\,KB uncompressed). The server then advances $L$ rounds. In each round about 20\% of resources change (at least one), and each changed resource has 3 of its 100 items modified. The client must bring all $N$ resources current. We vary $N\in\{1,10,50,100\}$ and $L\in\{1,5,25\}$.

Every system runs over real sockets behind a TCP proxy that counts bytes in both directions, counts connections, and adds a 40\,ms round-trip time plus one RTT per new connection. Bytes include all HTTP headers and HTTP/2 framing but not TCP or TLS handshakes; the connection counts indicate where handshakes would add cost. Each client's reconstructed state is compared with the server's, and any mismatch aborts the run. Connections are cold, as when an application resumes. Wall time is the median of three runs. Two profiles are used: \emph{lab} (minimal request headers, no compression) and \emph{realistic} (a bearer token, a cookie, browser-style headers, and gzip on bodies above 1\,KB where the server supports it). Item text is drawn from a seeded vocabulary so that compressibility is not unrealistically high.

\paragraph{Systems compared.} Two baselines: full \texttt{GET}s ($N$ requests over HTTP/1.1 with six keep-alive connections) and \texttt{GET} with \texttt{If-None-Match}. Two pieces of real third-party software:
\begin{itemize}
  \item \textbf{Braid (real)}: the \texttt{braid-http} library (v1.5.1), with \texttt{braidify} on the server and its \texttt{fetch} on the client, one \texttt{GET} with \texttt{Parents} per resource. Updates are Braid range patches with JSON Pointer ranges, one per changed item. Its Node client runs over HTTP/1.1 here, because cleartext rules out HTTP/2 negotiation. We also run it with subscriptions and its multiplexing extension forced on (\textbf{Braid mux}): one \texttt{POST} creates a multiplexer and each resource is still requested with its own \texttt{GET}, with responses carried on the multiplexer stream.
  \item \textbf{Mercure (real)}: the Mercure.rocks hub~1.1.0 (Docker image \texttt{dunglas/mercure}) with its default history store. The history is published before measurement; the client subscribes with $N$ topic matchers and \texttt{Last-Event-ID} and disconnects once it has received the expected events.
\end{itemize}
\emph{Models} written for this study cover cases the real software could not exercise here: a Braid-style exchange over cleartext HTTP/2 with all requests multiplexed on one connection, and Braid-style and Mercure-style servers with gzip enabled. \textbf{SYNC} is the reference handler on an ordinary Node.js HTTP server, receiving one \texttt{QUERY}. The SYNC handler and the models use the same JSON Patch generator and the same ``snapshot if smaller'' rule.

\paragraph{Against full polling.} Every delta mechanism saves most of the bytes when $L$ is small. Conditional \texttt{GET} helps only when many resources are unchanged: at $N=100$, $L=1$ it transferred 17--28\% of full \texttt{GET}, and at $L=25$, with every resource changed, it saved nothing.

\paragraph{Lab profile.} With minimal headers and no compression, SYNC, the real Mercure hub, and the HTTP/2 Braid model are close at $N=100$, $L=1$ (1.0\%, 1.1\%, and 1.0\%; 21.9\,KB, 23.6\,KB, and 20.0\,KB). Real Braid used 2.8\%, because each of the 100 requests carries its own headers and its own connection. For a single resource SYNC is not smaller than the alternatives (7.4\% against 6.5\% for real Braid). When many changes accumulate ($L=25$), real Braid is the smallest (22.4\% against 24.6\% for SYNC at $N=100$). This is a patch-format effect: Braid's range patches replace whole items, while JSON Patch emits one operation per changed field. SYNC's format negotiation could carry an equivalent format.

\paragraph{Realistic profile.} With request headers and compression, SYNC is the smallest in every configuration with more than one resource: at $N=100$, $L=1$ it transferred 5.2\,KB, against 25.1\,KB for the real Mercure hub, 36.0\,KB for the HTTP/2 Braid model, and 108.5\,KB for real Braid. Part of the gap to the real software is that neither compresses responses in its default configuration. The Braid model, which does compress, isolates the protocol effect: one request carries one set of headers instead of $N$, and one large body compresses better than $N$ small ones. We have not separated these two effects.

\paragraph{History replay.} Mercure replays every intermediate event rather than the net change. At $N=1$, $L=25$ this cost 137\% (lab) and 534\% (realistic) of a full \texttt{GET}. That is the right behavior when history is wanted and a cost when only current state is.

\paragraph{Multiplexing.} In this Node setup, Braid's multiplexed mode used roughly twice the bytes of its plain mode and still opened a connection per request. Its purpose is to keep many long-lived subscriptions within a browser's per-host connection limit, which this measurement does not exercise, so it should not be read as a verdict on multiplexing.

\paragraph{Time and connections.} With a 40\,ms RTT, request count dominates over HTTP/1.1 with a connection pool: at $N=100$, pooled per-resource \texttt{GET}s took about 750--850\,ms, while SYNC, the Mercure hub, and real Braid took about 95--110\,ms at $L=1$. Real Braid achieves its time by opening one connection per resource (100 at $N=100$). Under TLS each of those adds a handshake that our byte counts exclude, whereas SYNC and Mercure use one connection. At $N=100$, $L=25$ in the lab profile the HTTP/2 model took 674\,ms against 135\,ms for SYNC; we suspect HTTP/2 flow-control windows across round trips but did not investigate.

\subsection{Limitations}

The real software was used in default configurations and driven by code written for this study; in particular, applying Braid's JSON range patches is application code, as the library leaves it to applications. The HTTP/2 and compressed Braid figures come from models, not from the Braid software. Mercure's subscriber disconnects after catching up, where a real subscriber would stay connected. The measurement is a single exchange over loopback with emulated latency; it does not model TLS, server load, packet loss, or bandwidth limits, and the data is synthetic. Shared caching of \texttt{QUERY} responses, which could help SYNC further when many clients share a state, was not measured. Only catch-up is measured: Braid and Mercure also provide live push, which SYNC does not.

\section{Security}
\label{sec:security}

The accompanying analysis enumerates attack vectors; we summarize them here, including which mitigations the reference implementation enforces.

\textbf{Authorization and caching.} Authorization must be applied per named resource, with unreadable resources indistinguishable from absent ones; the store receives the request context for this purpose. Because \texttt{QUERY} responses are cacheable, responses that depend on authorization must not be stored by shared caches; the reference handler sends \texttt{no-store} by default.

\textbf{Replay and rollback.} A patch applied against a baseline other than the one it was computed from corrupts state; the client checks \texttt{from} against its baseline (implemented). Full representations carry no such check, so where freshness matters tokens should be ordered or signed.

\textbf{Probing tokens.} Any resume-token mechanism lets a requester distinguish recognized from unrecognized tokens; Mercure documents a related concern for its event identifiers. Tokens should be unguessable where change history is sensitive. The reference implementation's demonstration data uses sequential tokens and must not be deployed as is.

\textbf{Resource consumption and compression.} A request multiplies per-request work, so limits are enforced and rate limits should count resources, not requests. Compressing results that echo request content alongside confidential data invites length-based attacks; \texttt{QUERY} requests and \texttt{POST} requests with this media type require a CORS preflight, which limits cross-origin influence.

The reference implementation does not provide TLS, authentication, rate limiting, or signed results.

\section{Discussion and Standardization}
\label{sec:discussion}

\paragraph{Composition rather than competition.}
Braid, Mercure, and Events Query address live synchronization. SYNC's contribution is a stateless catch-up for many resources, which is the step a client performs before opening those streams. The measurements suggest that its value is greatest when many resources are involved and per-request overhead is not negligible; for a single resource the difference from per-resource requests is small and goes either way. Whether multi-resource catch-up is better specified as a separate format or as an extension of Braid's versioning and update model is an open question we intend to pursue with the Braid authors.

\paragraph{Standardization path.}
Because SYNC is a format for an existing method, standardizing it means registering its two media types and its header field in a specification, rather than registering a method. The draft specification and its open questions (non-JSON representations, sets of version identifiers, canonical request forms for caching, partial results, and venue) are in the repository.

\section{Conclusion}

HTTP lacks a standard way to catch up many resources in one stateless exchange. Existing efforts cover parts of this space: Braid for per-resource baselines and live updates, Mercure and Events Query for push, JMAP for a complete application protocol. SYNC is a small query format for the \texttt{QUERY} method that combines client-declared baselines, many resources per request, per-resource results, and negotiated update formats, and inherits \texttt{QUERY}'s caching and deployment properties. Measured against the Braid library and the Mercure hub, its advantage is real but conditional: largest when many resources are caught up under realistic header and compression overheads, comparable to Mercure when overheads are minimal, behind Braid's item-level patches when many changes accumulate, and absent for a single resource. The implementation, tests, benchmark, specification, and security analysis are available at \url{https://github.com/Meet-1010/sync-http-method}.
