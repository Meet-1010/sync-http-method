\author{Meet Chauhan\\

\begin{abstract}
Applications that hold local copies of several server resources must periodically bring all of them up to date. HTTP gives no standard way to say, for many resources at once, ``this is what I already have; send only what changed.'' Related efforts address parts of this space: Braid-HTTP lets a \texttt{GET} carry a baseline for a single resource, Mercure and Events Query push updates over long-lived connections, and JMAP defines a complete application protocol. We describe SYNC, a safe and idempotent HTTP method that occupies one narrow combination of these designs: a client declares a baseline for each of many resources in one request, and the server returns an independent per-resource result (a JSON Patch, a JSON Merge Patch, or a full snapshot) in one response, with no long-lived connection and no failure coupling between resources. We present a reference implementation, a security analysis, and a measurement comparing SYNC with full-resource polling, conditional GET, and models of Braid-style and Mercure-style catch-up over real sockets with simulated latency. In a setting with realistic request headers and response compression, SYNC transferred 1.3\% of the bytes of full polling to catch up 100 resources after one round of change, versus 6.8\% for per-resource HTTP/2 requests with a baseline header and 3.7\% for a Mercure-style replay. With minimal headers and no compression the three are within a few percent of each other, and for a single resource the differences are small and go either way. We discuss where batching helps, where it does not, and how SYNC composes with subscription-based approaches.
\end{abstract}

\section{Introduction}

Applications that keep local state synchronized against a server (feed readers, mobile apps resuming after being offline, dashboards, configuration agents, caches) share a common step: the client holds copies of several resources and needs to bring them current. Most of the data it would receive is data it already has.

HTTP offers two standard tools for this. A plain \texttt{GET} returns the full representation every time. A conditional \texttt{GET} with an entity tag returns either the full representation or \texttt{304 Not Modified}~\cite{rfc9110}, so a resource that changed in one field is re-sent in full. Applications therefore either accept that cost, or build ad hoc mechanisms: delta tokens in query parameters, custom endpoints, or WebSocket protocols.

This is not an unexplored problem, and we do not claim it is. Section~\ref{sec:related} surveys related work. Braid-HTTP~\cite{braid} already lets a client send a \texttt{Parents} header on a \texttt{GET} and receive only the updates since that version, for one resource at a time. Mercure~\cite{mercure} and Events Query~\cite{eventsquery} deliver updates over long-lived connections. JMAP~\cite{rfc8620} and WebDAV collection synchronization~\cite{rfc6578} provide ``changes since a state token'' within their own protocols.

SYNC targets a narrower point in this space. It is a \emph{stateless pull} that names \emph{many resources in one request} and returns an \emph{independent result for each}. The intent is to compose with, not replace, subscription mechanisms: a client resuming after a disconnect can SYNC once for all of its resources and then open streams for live updates.

\paragraph{Contributions.}
\begin{itemize}
  \item The definition of SYNC: a safe, idempotent method carrying a baseline per resource, returning per-resource results in a negotiated update format, with defined failure isolation (Section~\ref{sec:method}).
  \item A reference implementation, with a client that refuses patches that do not match its held baseline, and a test suite (Section~\ref{sec:impl}).
  \item A measurement comparing SYNC with GET, conditional GET, and models of Braid-style and Mercure-style catch-up on real sockets, under minimal and realistic header and compression conditions, including conditions where SYNC does \emph{not} help (Section~\ref{sec:eval}).
  \item A security analysis of client-declared-baseline protocols that states which mitigations the reference implementation does and does not enforce (Section~\ref{sec:security}).
\end{itemize}

\section{Related Work}
\label{sec:related}

\paragraph{Conditional GET and delta encoding.}
Entity tags~\cite{rfc9110} give a binary answer. RFC~3229~\cite{rfc3229} adds delta encoding to \texttt{GET}, but the server selects the baseline from its own history and the client cannot declare which version it holds; deployment was minimal.

\paragraph{Braid-HTTP.}
Braid~\cite{braid,braidversions} generalizes HTTP towards state synchronization with four extensions: versioning (\texttt{Version} and \texttt{Parents} headers forming a version DAG), updates as patches or snapshots, subscriptions (\texttt{Subscribe}, \texttt{209}), and merge types for CRDT and operational-transform behavior. A \texttt{GET} with a \texttt{Parents} header returns the updates since that version, and JSON Patch is an allowed patch type. This is the closest prior art to the single-resource form of SYNC, and it covers much more: live streams and multi-writer merging are outside SYNC's scope. Braid operates per URI; a client tracking $N$ resources issues $N$ requests or opens $N$ subscriptions. The published drafts have expired, and the latest Braid-HTTP draft does not yet contain its security considerations.

\paragraph{Mercure and Events Query.}
Mercure~\cite{mercure} is a publish/subscribe hub over Server-Sent Events with topic matchers, OAuth-based authorization, and \texttt{Last-Event-ID} resumption. Its resumption cursor is hub-wide rather than per resource, history may be discarded, and it requires a held connection. Events Query~\cite{eventsquery} uses the \texttt{QUERY} method~\cite{rfc10008} to return a representation and a notification stream from a single resource. It lists multi-resource delivery as a limitation and places versioning and resumption out of scope. SYNC addresses both for the pull case.

\paragraph{JMAP and WebDAV synchronization.}
JMAP~\cite{rfc8620} defines \texttt{/changes} methods returning changes since a client-supplied state string and batches method calls in one request. It is a full application protocol with its own object model and endpoint. WebDAV collection synchronization~\cite{rfc6578} provides a \texttt{sync-token} for the members of one collection. SYNC differs in being a generic HTTP method over arbitrary JSON resources.

\paragraph{WebSockets, SSE, and application-layer schemes.}
WebSockets~\cite{rfc6455} and Server-Sent Events provide push over persistent connections, with the costs in statefulness and intermediary compatibility that follow. Application-level schemes such as CouchDB's replication protocol and the delta queries of Microsoft Graph demonstrate demand but are not interoperable across APIs.

\paragraph{QUERY.}
\texttt{QUERY}~\cite{rfc10008} is a safe, idempotent method that carries a request body but defines no synchronization semantics. SYNC could alternatively be specified as a \texttt{QUERY} with a defined media type; Section~\ref{sec:discussion} discusses the tradeoff.

\section{The SYNC Method}
\label{sec:method}

\subsection{Semantics}

A SYNC request carries a \emph{baseline} for each of one or more resources: an opaque version token naming the state the client holds, or \texttt{null} for none. (An earlier revision called this structure a ``version vector''. That term denotes per-replica counters in distributed systems, which this structure is not, so it was renamed.) The server resolves each resource independently and returns one result per resource. SYNC is safe and idempotent in the sense of RFC~9110, so clients and intermediaries may retry it.

\begin{lstlisting}[style=code]
SYNC /api/sync HTTP/1.1
Content-Type: application/sync-baseline+json
Accept: application/sync-result+json

{
  "baselines": { "/users": "a4f2", "/posts": "7b1e", "/config": null },
  "accept": ["application/merge-patch+json",
             "application/json-patch+json"]
}
\end{lstlisting}

Tokens are opaque to the client; the server alone defines which it recognizes. This keeps the method independent of the versioning scheme: counters, content hashes, or Braid version identifiers can all be used.

\subsection{Per-Resource Results}

The response carries a result for every requested resource:

\begin{lstlisting}[style=code]
{
  "results": {
    "/users":  { "status": 200,
                 "format": "application/merge-patch+json",
                 "from": "a4f2", "to": "c93b",
                 "data": { "/users/1": { "email": "new@example.com" } } },
    "/posts":  { "status": 304, "to": "7b1e" },
    "/config": { "status": 200, "format": "application/json",
                 "from": null, "to": "5d0e", "data": { "timeout": 30 } },
    "/gone":   { "status": 404 }
  }
}
\end{lstlisting}

The HTTP status is \texttt{200} when any result is other than \texttt{304} and \texttt{204} when every resource is unchanged. Per-resource statuses are \texttt{200} (update present), \texttt{304} (unchanged), \texttt{404} (no such resource), and \texttt{409} (baseline unrecognized, only when the client sets \texttt{recover} to false). By default an unrecognized baseline is answered with a full snapshot, so the client recovers in the same round trip. A failure for one resource never prevents results for the others. This is the property that makes batching useful in practice: with a single status for the whole request, one stale token among a hundred would force the client to retry everything.

\subsection{Update Formats}

Three formats are defined: JSON Patch~\cite{rfc6902} (whose paths are JSON Pointers~\cite{rfc6901}), JSON Merge Patch~\cite{rfc7396}, and a full snapshot. The client lists acceptable media types in preference order. For each resource the server uses the first format in which the change is expressible and falls back to a snapshot when the update is not smaller than the snapshot. Merge Patch cannot express a \texttt{null} member, so changes involving one are sent in the next preferred format. A snapshot is always a valid answer, so clients must handle it for any resource. Other formats can be registered later.

\subsection{Header Form and Limits}

For small requests, baselines may be carried in a \texttt{Sync-Baseline} header as an RFC~8941~\cite{rfc8941} list of inner lists of strings, for example \texttt{("/users" "a4f2"), ("/config")}. (A Structured Fields dictionary is unsuitable because dictionary keys cannot contain \texttt{/}.) Servers must bound the cost of a request: the reference server rejects more than 100 resources or a body over 64\,KiB with \texttt{413}, and oversized header sections with \texttt{431}.

\subsection{Client Behavior}

Before applying a patch, the client must check that the result's \texttt{from} equals the baseline it holds, and discard the result otherwise. A response replayed from a cache, or computed against a different baseline, would otherwise silently corrupt local state. If applying any operation fails, local state is left unchanged.

\section{Reference Implementation}
\label{sec:impl}

\subsection{Why \texttt{net.createServer}}

Node.js's HTTP parser (llhttp) rejects methods outside a fixed list with \texttt{400} before any application code runs, so SYNC cannot be added through framework middleware. The reference server therefore accepts raw TCP connections, buffers until it has the request line, and routes SYNC requests to its own handler while proxying every other method to an internal Express server on a loopback port. The same pattern applies to any runtime that validates methods at the parser layer.

\subsection{Components}

The server comprises: a per-resource resolver implementing the semantics of Section~\ref{sec:method}; a delta engine producing JSON Patch (via \texttt{fast-json-patch}), Merge Patch, or a snapshot; a pluggable, possibly asynchronous store interface (the resolver needs only ``current state'' and ``state at token''; a store that cannot reconstruct an old token simply causes a snapshot to be sent); and the transport layer enforcing size limits, keep-alive across consecutive SYNC requests, and optional gzip. The client library provides the request function, a map of held tokens, and a function that applies results and refuses patches that do not match the held baseline.

\paragraph{Deployability.} Because many servers, proxies, CDNs, and WAFs reject unknown methods (Node.js does so in its parser), the reference implementation also serves a \emph{POST compatibility form}: a \texttt{POST} with the SYNC media type is processed identically, as an Express middleware that works on any existing application. The client tries the SYNC method first, falls back to the POST form on \texttt{400}, \texttt{405}, \texttt{501}, or a connection reset, and remembers the choice per origin. The cost is that generic intermediaries do not know the POST is safe and idempotent. In the Node reference server a connection that mixes SYNC with other methods is not supported, because the first non-SYNC request hands the rest of the connection to Express; the POST form avoids this.

A suite of 65 automated tests covers per-resource failure isolation, format negotiation and fallback, the header form (including parsing of resource names containing quotes and commas), limits, compression, resource names such as \texttt{\_\_proto\_\_}, keep-alive and pipelined requests, the POST form, client fallback against a server that rejects SYNC, an asynchronous recent-only store, a failing store, and end-to-end application of results against server state. Writing the suite exposed two defects in earlier versions of the server, both now fixed and covered by regression tests: a request body of \texttt{null} crashed the process, and large request bodies passed through to the Express side could be silently dropped.

\section{Evaluation}
\label{sec:eval}

\subsection{Setup}

A client holds $N$ resources at round~0, each a JSON object of 100 items (about 20\,KB uncompressed). The server then advances $L$ rounds. In each round about 20\% of resources change (at least one), and each changed resource has 3 of its 100 items modified. The client must bring all $N$ resources current. We vary $N\in\{1,10,50,100\}$ and $L\in\{1,5,25\}$.

All protocols run over real loopback sockets behind a TCP proxy that counts bytes in both directions and adds a 40\,ms round-trip time (plus one RTT per new connection). Bytes therefore include all HTTP headers and HTTP/2 framing; TLS is not modelled. Each client's reconstructed state is compared with the server's, and any mismatch aborts the run. Connections are cold, as when an application resumes. Wall time is the median of three runs. Two header and compression profiles are used: \emph{lab} (minimal request headers, no compression) and \emph{realistic} (a bearer token, a cookie, browser-style headers, and gzip on bodies above 1\,KB). Item text is drawn from a seeded vocabulary so that compressibility is not unrealistically high.

The protocols compared are: full \texttt{GET}s ($N$ requests, HTTP/1.1, six keep-alive connections); \texttt{GET} with \texttt{If-None-Match}; a \emph{Braid-style} per-resource \texttt{GET} with a \texttt{Parents} header returning a JSON Patch or \texttt{304}, over both HTTP/1.1 and cleartext HTTP/2 with all requests multiplexed; a \emph{Mercure-style} single request with $N$ topic matchers and \texttt{Last-Event-ID}, in which the hub replays every intermediate event; and SYNC itself. All delta protocols use the same JSON Patch generator and the same ``snapshot if smaller'' rule, so differences arise from protocol framing, request count, and coalescing rather than the diff algorithm.

\paragraph{Against full polling.} All delta mechanisms save most of the bytes when $L$ is small. Conditional \texttt{GET} helps only when many resources are unchanged: at $N=100$, $L=1$ it transferred 17--28\% of full \texttt{GET}, but at $L=25$, where every resource had changed, it saved nothing (100.2--100.6\%).

\paragraph{Lab conditions: no clear winner.} With minimal headers and no compression, Braid-style HTTP/2, Mercure-style replay, and SYNC are within a few percent of one another. For a single resource ($N=1$), the Braid-style request is smaller than SYNC (6.1\% versus 7.1\% at $L=1$), because SYNC pays for a request body. SYNC offers no byte advantage here. In the realistic profile the single-resource result is mixed: SYNC is smaller at $L=1$ (26.3\% versus 31.3\%) and larger at $L=5$ (39.9\% versus 33.0\%).

\paragraph{Realistic conditions: batching helps.} With request headers and compression, per-request overhead matters. At $N=100$, $L=1$, SYNC transferred 6.7\,KB, against 36.0\,KB for Braid-style HTTP/2, 90.2\,KB for Braid-style HTTP/1.1, and 19.8\,KB for the Mercure-style replay (which, as modelled, is not compressed). Two effects contribute: one request carries one set of headers instead of $N$, and one large body compresses better than $N$ small ones. We have not separated the two effects experimentally.

\paragraph{Large $L$.} As $L$ grows the delta approaches the full state. At $N=1$, $L=25$ the Braid-style and SYNC requests send 74--93\% of the bytes of a full \texttt{GET}. The Mercure-style replay can exceed full polling (130\% in the lab profile and 504\% in the realistic profile at $N=1$, $L=25$) because it delivers every intermediate patch rather than the net change; this is appropriate when history is wanted and wasteful when it is not.

\paragraph{Time.} With a simulated 40\,ms RTT, request count dominates over HTTP/1.1: at $N=100$, per-resource HTTP/1.1 requests took about 750--850\,ms, whereas SYNC, the Mercure-style stream, and HTTP/2 multiplexing took roughly 95--115\,ms at $L=1$. At $N=100$, $L=25$ in the lab profile the HTTP/2 run took 639\,ms against 117\,ms for SYNC; we suspect HTTP/2 flow-control windows across round trips but did not investigate.

\subsection{Limitations}

The Braid-style and Mercure-style servers are minimal models written for this study from the published drafts, not the projects' own software, and Mercure's stream is closed after replay where a real subscriber would hold it open. The measurement is a single exchange over loopback with emulated latency; it does not model TLS, server load, packet loss, or bandwidth limits. Data is synthetic. Only catch-up is measured: Braid and Mercure also provide live push, which SYNC does not. A fuller evaluation would use the projects' reference implementations and real application traces.

\section{Security}
\label{sec:security}

The analysis in the accompanying document enumerates attack vectors; we summarize them here, including which mitigations the reference implementation enforces.

\textbf{Replay and rollback.} A patch applied against a baseline other than the one it was computed from corrupts state. The client checks \texttt{from} against the held baseline (implemented). Snapshots carry no such check, so where freshness matters tokens should be ordered or signed.

\textbf{Baseline probing.} Any resume-cursor protocol lets a prober distinguish recognized from unrecognized cursors; Mercure documents a related leak for its event cursors. In SYNC the distinction appears as patch versus snapshot, or as \texttt{409} when recovery is disabled. Tokens must be opaque and unguessable. The reference server's demonstration data uses sequential tokens and must not be deployed as is.

\textbf{Amplification.} A batch multiplies per-request work, and a rate limiter that counts requests would undercount. The reference server caps resources per request and body size (implemented); time bounds and rate limiting are not.

\textbf{Per-resource authorization and compression.} Authorization must be applied per resource, with forbidden resources indistinguishable from nonexistent ones. Compressing results that mix secrets with request-controlled text (resource names are echoed) invites length-based attacks; SYNC is not a CORS-safelisted method, which narrows the cross-origin path.

The reference server does not implement TLS, authentication, rate limiting, or signed results.

\section{Discussion and Standardization}
\label{sec:discussion}

\paragraph{Composition rather than competition.}
Braid, Mercure, and Events Query solve live synchronization. SYNC's contribution is a stateless catch-up for many resources, which is the step a client performs before opening those streams. The measurements suggest the value is greatest when many resources are involved and per-request overhead is not negligible; for a single resource the difference from per-resource requests is small and goes either way.

\paragraph{Method or profile.}
Since the publication of RFC~10008, SYNC could be defined as a \texttt{QUERY} with a defined media type, avoiding a new method registration and deploying on infrastructure that already tolerates \texttt{QUERY}. A new method gives clearer semantics and independent evolution; a \texttt{QUERY} profile has lower deployment cost. We regard this as an open question for the HTTP working group.

\paragraph{Open questions.}
Whether a recommended token encoding should align with Braid version identifiers; whether and how SYNC responses may be cached; whether omission of resources suffices to express partial responses; and which additional update formats should be registered. An early version of this proposal was posted to the IETF HTTP working group mailing list, and feedback received there motivated the redesign described in this paper: the renaming of the version-vector structure, the decoupling from a single update format, and the per-resource result model.

\section{Conclusion}

HTTP lacks a standard way to catch up many resources in one stateless exchange. Existing efforts cover parts of this space: Braid for per-resource baselines and live streams, Mercure and Events Query for push, JMAP for a complete application protocol. SYNC is a small method that combines client-declared baselines, many resources per request, per-resource results, and negotiated formats. Our measurements show that its advantage is real but conditional: it is largest when many resources are caught up under realistic header and compression overheads, comparable to alternatives when overheads are minimal, and small and inconsistent in sign for a single resource. We release the reference implementation, tests, benchmark, specification, and security analysis at \url{https://github.com/Meet-1010/sync-http-method}, and welcome comparison against the Braid, Mercure, and Events Query reference implementations.
