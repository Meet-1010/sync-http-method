\begin{abstract}
Applications that hold local copies of many server resources must keep them synchronized. Doing so one request per resource has four costs that grow with the number of resources: per-request overhead; \emph{torn reads}, in which separate requests combine related resources in a way that never existed; load on the origin when many clients reconnect at once; and \emph{partial writes}, in which a change to related resources is applied in part and seen half done. We describe SYNC, a query format for the HTTP \texttt{QUERY} method (RFC~10008) and a companion format for \texttt{POST}, that addresses all four. A client states the version it holds of each of many resources and receives an independent result for each: a patch (the smallest of the formats it accepts), ``unchanged'', or the full representation, for any media type. It can ask for every result to come from one snapshot, keep receiving the net changes in one stream with transactions kept whole, and change several resources atomically, with concurrent changes to different parts of a resource merged by the server. Every response can name the URI of the client's next catch-up, which all clients in the same state share, so that ordinary shared caches carry catch-up for a whole population. We evaluate a reference implementation (219 tests) against the \texttt{braid-http} library, the Mercure hub and plain HTTP in five measurements over real sockets. When 100 or 500 clients reconnected at once through a shared cache, the origin received one request and sent 40\,KiB, against 50 requests for per-resource Braid requests made cacheable and 4.3\,MiB to 21.5\,MiB from the Mercure hub. With realistic timing, 79\% and 82\% of reads made with parallel \texttt{GET} and Braid requests combined resources that never existed, and none with SYNC's snapshots. Live, 100 clients received each whole transaction in 38\,ms (median), without ever holding a state that did not exist, where per-resource subscriptions showed such states in 92\% of updates. Atomic transfers ran 1.9 times as fast as pairs of conditional \texttt{PUT}s with no wrong totals visible (against 92\% of reads), and merged concurrent edits to one document lost nothing, with 1 retry where \texttt{If-Match} needed 900.
\end{abstract}

\section{Introduction}

Applications that keep local state synchronized with a server (mobile applications resuming after being offline, dashboards, collaborative editors, configuration agents) hold copies of many resources and must keep them current, and often change several of them together.

HTTP offers per-resource tools. A conditional \texttt{GET} returns the full representation or \texttt{304 Not Modified}~\cite{rfc9110}; Braid-HTTP~\cite{braid} lets a \texttt{GET} state the version the client holds and returns only the updates since, and adds subscriptions and \texttt{PUT} with versions; Mercure~\cite{mercure} pushes events from a hub. Working one resource at a time has four costs:

\begin{enumerate}
  \item \textbf{Overhead.} Each request carries its own headers and often its own connection.
  \item \textbf{Inconsistency.} Separate requests observe the server at different moments, so a client can assemble related resources (a post and its author, an order and its lines) in a combination that never existed: a \emph{torn read}. The same happens with per-resource streams of live updates.
  \item \textbf{Load concentration.} After an outage, many clients reconnect at once, typically from the same state. Unless shared caches can answer them, the origin computes and sends the same catch-up to each.
  \item \textbf{Partial writes.} Changing related resources takes several requests. If one fails, the others have been applied, and other clients can observe the state in between.
\end{enumerate}

SYNC is a query format for \texttt{QUERY}~\cite{rfc10008} in which a client names many resources, with the version it holds of each, in one request, and receives an independent result per resource. On this base it provides consistent snapshots, a stream of whole transactions, atomic changes with merging, and three mechanisms that let ordinary shared caches carry the traffic: shared results, next URIs and links.

An earlier version of this proposal, posted to the IETF HTTP working group, defined a new HTTP method; discussion there showed that \texttt{QUERY} provides what a new method would, and SYNC is now a format for it. Feedback from the Braid authors led to versions that are sets of identifiers, as in Braid, and to support for any media type.

\paragraph{Contributions.}
\begin{itemize}
  \item A query format for \texttt{QUERY} with per-resource results for any media type, versions that are sets of identifiers, the smallest patch among the formats a client accepts, and a splice format for text and binary content (Section~\ref{sec:design}).
  \item Consistent snapshots across resources, confirmed by the server (Section~\ref{sec:consistency}).
  \item Three ways for today's shared caches to carry catch-up: \emph{shared results} (a \texttt{303} redirect to the results at one state), \emph{next URIs} (the client's next catch-up as a \texttt{GET}, the same for every client in the same state), and \emph{links} to immutable updates (Section~\ref{sec:sharing}).
  \item \emph{Watching}: one stream of the net changes to many resources, with transactions delivered whole and access evaluated per event (Section~\ref{sec:watch}).
  \item \emph{Atomic changes} to several resources with a precondition per resource, and server-side merging of concurrent changes to different parts of JSON, text and binary representations (Section~\ref{sec:writes}).
  \item A reference implementation and five measurements against \texttt{braid-http}, the Mercure hub and plain HTTP, including where SYNC does not win (Sections~\ref{sec:impl} and~\ref{sec:eval}).
\end{itemize}

\section{Related Work}
\label{sec:related}

\paragraph{Braid-HTTP.}
Braid~\cite{braid,braidversions} extends HTTP towards state synchronization: versions are sets of identifiers forming a directed acyclic graph, a \texttt{GET} with \texttt{Parents} returns updates since a version, subscriptions push later updates, \texttt{PUT} carries patches with versions, and merge types resolve concurrent edits. Requests and subscriptions are per resource; a multiplexing extension~\cite{braidmux} carries many subscriptions over one connection. SYNC adopts Braid's versions and \texttt{Version} and \texttt{Parents} fields, and adds what is missing across resources. Braid's merge types resolve concurrent edits to the same part of a resource, which SYNC reports as conflicts.

\paragraph{Mercure and Events Query.}
Mercure~\cite{mercure} is a publish/subscribe hub over Server-Sent Events that resumes from a hub-wide event identifier by replaying every event since. Events Query~\cite{eventsquery} uses \texttt{QUERY} to return a representation and notifications for one resource, and lists multi-resource delivery and resumption as out of scope.

\paragraph{Batching and transactions.}
JMAP~\cite{rfc8620} returns changes since a state string and applies sets of changes within its own object model; OData batches can group operations atomically within its protocol. WebDAV collection synchronization~\cite{rfc6578} provides a token for one collection. GraphQL batches reads without versions or updates. SYNC is a generic format for resources identified by URI, and its atomic changes use a per-resource precondition, like \texttt{If-Match}, across resources.

\paragraph{Snapshots, merging and caching.}
Databases avoid torn reads with snapshot isolation~\cite{berenson1995}; HTTP has no cross-resource equivalent. Operational transformation~\cite{ellis1989} and CRDTs~\cite{shapiro2011} merge concurrent edits; SYNC's merging is a conservative transformation that applies a change only if it touches parts that did not change. Application sync engines such as Replicache notify clients and let them pull; SYNC's next URIs and event links make the pulled content cacheable by ordinary HTTP caches~\cite{rfc9111}.

\section{Design}
\label{sec:design}

\subsection{Why QUERY}

A safe, idempotent request whose content describes what to return is what \texttt{QUERY} provides, with defined caching (the content is part of the cache key), conditional requests, and ways to give results a URI~\cite{rfc10008}. A new method would add none of these and would be rejected by parsers and intermediaries: Node.js~26 rejects an unknown method before application code runs, while it accepts \texttt{QUERY}. SYNC is therefore a media type, \texttt{application/sync-baseline+json}, sent with \texttt{QUERY} to a \emph{sync resource}, with a \texttt{POST} fallback.

\subsection{Versions, Requests and Results}

A version is a non-empty set of version identifiers, equal to another when equal as sets; a version names exactly one state of its resource. Because the update between two given versions is then fixed, a server can reuse it across clients and give it a URI that caches may keep; this one requirement underlies Sections~\ref{sec:sharing} and~\ref{sec:watch}.

\begin{lstlisting}[style=code]
QUERY /sync HTTP/1.1
Content-Type: application/sync-baseline+json

{ "baselines": { "/users": "a4f2", "/doc.md": ["alice-17", "bob-9"],
                 "/logo.png": null },
  "accept": ["application/merge-patch+json",
             "application/json-patch+json",
             "application/sync-splice+json"],
  "consistent": true, "next": true }
\end{lstlisting}

A \emph{baseline} is the version the client holds, or \texttt{null}. Resource names are absolute paths on the origin of the sync resource, and each is subject to the same access control as a \texttt{GET} of it; a resource the requester may not read is reported like an absent one. The response is \texttt{204} when nothing changed, and otherwise carries a result per resource: \texttt{200} with an update, \texttt{304}, \texttt{404}, or \texttt{409} (an unknown baseline, only when the client disables recovery; by default it receives the full representation in the same round trip). A failure for one resource never affects another.

\subsection{Updates for Any Media Type}

JSON types are carried as JSON values, text types as UTF-8 text, and all others as octets. Updates are JSON Patch~\cite{rfc6902} or JSON Merge Patch~\cite{rfc7396} for JSON types, and a \emph{splice} document for others: ordered, non-overlapping replacements \texttt{[start, deleteCount, insert]}, counted in code points for text and in octets for binary content. The client lists the formats it can apply; the server computes each that applies and sends the smallest, or the full representation when no patch is smaller. For text, it refines a line-based diff to the words that changed within each changed block, and compares the result with the single changed span of the whole text. Results come in a JSON format or as \texttt{multipart/mixed}~\cite{rfc2046}, with Braid's \texttt{Version} and \texttt{Parents} fields per part.

\subsection{Consistent Snapshots}
\label{sec:consistency}

With \texttt{"consistent": true} the server either computes every result from the states of the requested resources at one instant and says \texttt{Sync-Consistent: ?1}, or says \texttt{?0}; a client that requires consistency treats anything else as failure. Without it, results can reflect different moments even within one request.

\subsection{Shared Results, Next URIs and Links}
\label{sec:sharing}

Shared caches store responses to \texttt{GET} but not, today, to \texttt{QUERY}. SYNC therefore gives catch-up three \texttt{GET}-able forms.

\emph{Shared results.} With \texttt{"redirect": true} a server may answer \texttt{303 (See Other)}, as RFC~10008 allows, with the URI of a resource whose \texttt{GET} returns the response the request would have received. The URI identifies the request and the version each result leads to, so clients in the same state receive the same URI and its content never changes. Unlike the URI that \texttt{Location} carries in a \texttt{2xx} response to \texttt{QUERY}, which identifies the query and whose results change, a shared result identifies the results at one state.

\emph{Next URIs.} With \texttt{"next": true} every response carries a \texttt{Sync-Next} field: the URI of the same request from the versions the results lead to. A \texttt{GET} of it is that request, processed when the \texttt{GET} arrives. Clients in the same state hold the same next URI, so a population that was current when it lost its connection reconnects with one \texttt{GET} per client that a cache answers, and the origin sees one request per state. The entity tag of a next-URI response identifies the state its results lead to, so a polling client confirms ``nothing changed'' with a conditional request. A client uses a next URI only while it holds exactly the versions it names.

\emph{Links.} With \texttt{"links": true} a server may replace a large update with the URI of an immutable resource holding it, which results for different states can share.

All three are subject to per-\texttt{GET} access control and expire when the server no longer keeps the versions involved; the client then sends an ordinary request.

\subsection{Watching}
\label{sec:watch}

With \texttt{"watch": true} and \texttt{Accept: text/event-stream}, the server responds with a stream of Server-Sent Events~\cite{html}. The first event brings every requested resource current; each later one carries the net change since the previous one. With \texttt{"consistent": true}, every event is computed from one snapshot of all requested resources, so changes committed together arrive together and the client never holds a combination that did not exist. Access is evaluated for every event. Changes that occur while an event is being written are combined into the next, so a slow reader receives the net change, not a backlog. When the stream breaks, the client sends its request again with the versions it holds; the baselines, not an event identifier, are the point of resumption. With links allowed, an event that several watchers receive can be sent as a link to a shared result, so that a cache serves its content once to all of them.

\subsection{Atomic Changes}
\label{sec:writes}

\begin{lstlisting}[style=code]
POST /sync HTTP/1.1
Content-Type: application/sync-changes+json

{ "changes": {
    "/doc.md": { "base": "v7", "format": "application/sync-splice+json",
                 "data": { "unit": "codepoint", "splices": [[120, 4, "SYNC"]] } },
    "/todos":  { "base": "t3", "format": "application/merge-patch+json",
                 "data": { "3": { "done": true } } } },
  "merge": true }
\end{lstlisting}

Each change names the version it was made from. The server applies all changes at one instant, so every snapshot and watcher sees all or none, or applies none, and reports a status per resource: \texttt{412} for a base that is not current, \texttt{409} for a conflict, \texttt{422} for an invalid change, \texttt{424} for a change not applied because another failed. With \texttt{"merge": true}, a change from an older version is applied to the current one when the two touch different parts: JSON Pointer paths for JSON, where all changes within one array conflict because positions shift; ranges for splices, where insertions at the same position are both kept. The response then gives the update from the client's own copy (its base with its change) to the merged version. Repeating a request is made safe by the \texttt{Idempotency-Key} header field~\cite{idempotency}, scoped to the requester.

\section{Reference Implementation}
\label{sec:impl}

\paragraph{Server.}
A Node.js request handler serves reads, watches, writes, links, shared results and next URIs on one path, and passes other requests on. Its store has two required functions (current state, state at a version) and three optional ones (a snapshot, change notification, and an atomic conditional write); each receives the request context for access control. Resolution has two steps: planning reads the versions each result connects, and materializing computes the update. A redirect or next URI plans only and encodes the plan in the URI, so any server instance can serve any URI without shared state. These URIs are deterministic authenticated encryptions (a synthetic IV from HMAC-SHA256, AES-256 in counter mode, keys from HKDF), with one canonical spelling each; plans are compressed before encryption and decompressed only after authentication.

Updates are memoized per store, since a version names one state. After a change, watchers that hold the same versions with the same options and credentials form a group; the event is planned and encoded once and written to every member, and is sent as a link only when the group has more than one member. A watcher still writing an earlier event leaves the group and catches up on its own. Writes plan every change, merge where allowed, and commit through the store's conditional write; a write that loses a race is planned again.

\paragraph{Client.}
The client is built on \texttt{fetch} and runs in browsers and Node.js. It tracks versions, applies results, refuses patches that do not start from what it holds, follows redirects, links and next URIs, watches with automatic resumption, writes with the smallest patch from what it holds, and serializes its state (including its next URI). We verified it in Chromium as well as Node.js.

\paragraph{Tests.}
219 automated tests cover the protocol, every media-type class, both result formats, consistent snapshots under concurrent writes, the three cacheable forms (determinism, immutability, expiry, access per requester, forgery and bit-flipping, canonical encoding, URI length limits, client fallback), watching (whole transactions, coalescing, removal, access per event, grouping across credentials, resumption, polling fallback), and writes (atomicity, preconditions, merging of JSON, text and binary changes, conflicts, races, idempotent retries per requester). A randomized test checks 400 pairs of concurrent text edits against an oracle. We checked the suite by mutation: removing the HMAC check, ignoring versions in next URIs, grouping watchers regardless of credentials, ignoring conflicts when merging, or applying changes without their preconditions each makes tests fail.

\subsection{Torn Reads}

A writer commits a transaction every 5\,ms that changes three related resources together; clients read them 300 times per approach and check invariants that hold in every committed state. With fixed delays (the case most favourable to parallel requests), 1.7\% of parallel \texttt{GET} reads and 3.0\% of Braid reads were torn. With realistic network and store timing, 79.3\% and 82.3\% were, and one SYNC request without a snapshot 60.0\%, because its server read the resources separately. SYNC with \texttt{consistent} was never torn (0 of 300; 95\% CI 0--1.3\%), at the same median latency (57\,ms).

\subsection{Concurrent Writes}

Ten writers transfer units between pairs of 20 accounts while readers read every account. With two conditional \texttt{PUT}s per transfer, undoing the first when the second fails, 91.7\% of reads saw a wrong total and 120 debits were undone; with one atomic SYNC write, no read saw a wrong total, nothing was undone, and transfers completed at 41.5 per second against 22.1. Ten writers then edited one text document concurrently, each edit replacing a few characters with a unique marker. Whole-document \texttt{PUT}s with \texttt{If-Match} lost nothing but needed 900 retries and 6.1\,MiB at 10.8 edits per second; without a condition, 180 of 200 acknowledged edits were lost. SYNC's merged splices lost nothing, needed one retry, transferred 226\,KiB, and ran at 148.7 edits per second.

\subsection{Limitations}

Everything runs on one machine over loopback with emulated latency, without TLS, packet loss or bandwidth limits, and the data is synthetic. The third-party software runs in default configurations and is driven by code written for this study; Braid's Node client cannot use HTTP/2 over cleartext, so HTTP/2 figures come from a model. Shared caches are nginx and Varnish on the same machine, not a distributed CDN. SYNC's merging reports concurrent edits to the same part of a resource as conflicts, where Braid's merge types resolve them; we did not compare with those. Shared results, next URIs and links help only for data that is the same for every requester; for per-user data they must be private.

\section{Security}
\label{sec:security}

\textbf{Access.} Access is evaluated per resource for every request, \texttt{GET} of a link, shared result or next URI, watch event and write. Responses that depend on the requester must not be stored by shared caches; the implementation sends \texttt{no-store} or \texttt{private} unless configured otherwise. Watchers share an event only if their credentials are the same; a test in which one of two watchers in the same state loses access shows that sharing regardless of credentials would leak data.

\textbf{URIs.} Links, shared results and next URIs can appear in logs and caches, so they are encrypted and reveal no resource names or versions, and authenticated so that they cannot be forged or altered, including by bit-flipping of the malleable ciphertext; a stateless server replays only requests it accepted.

\textbf{Writes.} Writes require a CORS preflight, are authorized per resource through the store, apply all or nothing, and merge only changes to parts that did not change since the client's base, so no writer's change is overwritten unseen. Idempotency keys are scoped to the requester.

\textbf{Other.} Clients check baselines before applying patches and validate splice documents; versions should be unguessable where history is sensitive; servers must bound resources per request, watches, and merge sizes (the last two are not implemented in the reference server); compressing results that echo request content invites length-based attacks, which preflight requirements limit.

\section{Discussion and Standardization}
\label{sec:discussion}

\paragraph{Composition with Braid.}
SYNC uses Braid's versions and is the multi-resource layer that Braid's per-resource requests, subscriptions and \texttt{PUT} lack: one request, consistent snapshots, transactions delivered whole, atomic writes, and catch-up that caches share. Where Braid is stronger, conflict-free merging of concurrent edits, a resource could declare a Braid merge type that the server applies instead of reporting a conflict; we list this as an open question and intend to pursue it with the Braid authors.

\paragraph{Standardization.}
SYNC is a set of formats for existing methods: standardizing it means registering four media types and three header fields, not a method. The draft specification and its open questions are in the repository.

\section{Conclusion}

Keeping many resources synchronized one request at a time costs overhead, shows clients states that never existed, concentrates load on the origin, and applies related writes in part. SYNC addresses all four with formats for HTTP's \texttt{QUERY} and \texttt{POST}: per-resource results for any media type with the smallest update, consistent snapshots, a stream of whole transactions, atomic changes with merging, and three ways for ordinary caches to carry catch-up. In our measurements it removed torn reads and torn live views, reduced a reconnect storm of 100 or 500 clients to one request at the origin, and made atomic transfers and concurrent edits faster and lossless compared with plain HTTP, while matching or exceeding Braid and Mercure in each of their own settings, except for conflict-free merging, the CPU efficiency of a Go hub, and the bytes of a model of Braid over HTTP/2 with minimal headers. The implementation, tests, benchmarks, specification and security analysis are available at \url{https://github.com/Meet-1010/sync-http-method}.
